# Развёртывание Korra 21 на сервере клиента

Чек-лист на один контур: от пустого VPS до работающего агента, к которому
клиент заходит через кабинет и который сам себя бэкапит в облако клиента.

Каждый шаг — команда и проверка результата. Шаг без проверки считается
невыполненным: половина находок прошлых раскаток была там, где «команда
отработала», а результат оказался другим.

Файлы рядом:

| Файл | Что это |
|---|---|
| `up.sh` | первый запуск и launcher для host updater |
| `host-bootstrap.py` | подготовка хоста, root-доступ, проверка, ротация и отзыв |
| `update.sh`, `updater.py` | host update/rollback с сохранённой операцией |
| `dependencies.lock.json` | точные версии общего документного стека |
| `env.template` | заготовка `.env` клиента (ключи и токены) |
| `backup.sh` | ежедневный бэкап в облако клиента |
| `PROVIDER.md` | как подключить провайдера модели |

Где что выполняется, помечено в заголовке шага: **[клиент]** — на сервере
клиента, **[наш]** — на нашем сервере с кабинетом.

## Что нужно собрать до начала

- Root-доступ на сервер клиента (пароль или ключ) и его IP.
- Сервер: 4 vCPU / 8 ГБ RAM / 60 ГБ диска — рабочий минимум. Локальное
  распознавание речи держит около 1 ГБ памяти в работе; на 8 vCPU 34 секунды
  речи расшифровываются за 16–24 секунды.
- Дайджест образа и доступ к реестру (шаг 4) — у владельца.
- Адрес прокси провайдера и ключ для этого контура — у владельца, см.
  `PROVIDER.md`.
- Токен Telegram-бота от BotFather и числовой Telegram ID клиента.
- Куда бэкапить: облако **клиента** (его S3, его диск). На наш сервер
  клиентские данные не кладутся — это жёсткое правило, а не предпочтение.
- Режим установки: штатный host CLI включает администрирование контейнера
  и хоста. Для установки без этих прав используйте флаг --no-admin.
  Подробности и границы отзыва: [host-admin-setup.md](../host-admin-setup.md).

## Шаги 1–2 [клиент]. Подготовка хоста

Подготовку выполняет host-bootstrap.py на шаге 6, после копирования проверенного
host kit и выбора неизменяемого образа. CLI использует пакеты Ubuntu/Debian:
Docker, UFW, fail2ban, OpenSSH и зависимости launcher/backup. Существующий
Docker и активный swap сохраняются; собственный swap создаётся при RAM до
8 GiB и отсутствии активного. Повторная установка
с теми же параметрами сохраняет ключ контура.

Перед изменениями CLI проверяет существующие firewall policies. Совместимый
активный UFW сохраняется; конфликтующая или неподтверждённая конфигурация
останавливает подготовку. Перед первым включением UFW CLI разрешает
указанный операторский SSH-порт. Передайте
реальный порт через --ssh-port, если он отличается от 22. Панель, служебный API
и отдельный административный SSH слушают loopback. CLI не меняет часовой пояс
хоста: при необходимости настройте его отдельно.

## Шаг 3 [клиент]. Каталог данных

Всё изменяемое состояние контура живёт в одном каталоге на хосте. Внутри
контейнера он виден как `/opt/data`. Владелец — uid 10000: под этим
пользователем работает движок, и он же должен владеть файлами, иначе первая
же запись упрётся в права.

```bash
install -d -m 755 /opt/korra
install -d -o 10000 -g 10000 -m 750 /opt/korra/data
```

`/opt/korra` — каталог раскатки: туда лягут полный host kit (launcher, updater,
backup, dependency lock, env template) и `IMAGE`. Данные держим отдельной папкой, чтобы бэкап и снос контура не
задевали скрипты.

**Проверка:**

```bash
stat -c '%u:%g %a %n' /opt/korra/data   # ожидается 10000:10000 750
```

Спрашиваем именно числа (`%u:%g`): имени пользователя 10000 на хосте нет, и
`%U:%G` честно ответит `UNKNOWN`. Сопоставление имени живёт внутри
контейнера — так и задумано.

Туда же кладём комплект — с нашей машины, из этого каталога репозитория:

```bash
scp up.sh update.sh updater.py host-bootstrap.py backup.sh dependencies.lock.json env.template \
  root@<ip-клиента>:/opt/korra/
ssh root@<ip-клиента> 'chown root:root /opt/korra /opt/korra/{up.sh,update.sh,updater.py,host-bootstrap.py,backup.sh,dependencies.lock.json,env.template}'
ssh root@<ip-клиента> 'chmod 755 /opt/korra /opt/korra/{up.sh,update.sh,updater.py,host-bootstrap.py,backup.sh}; chmod 644 /opt/korra/{dependencies.lock.json,env.template}'
ssh root@<ip-клиента> '/opt/korra/update.sh --capabilities'
```

## Шаг 4 [клиент]. Образ из реестра

Образ лежит в GHCR приватным пакетом:
`ghcr.io/ceremoneymeister-bit/korra.twenty.one`. Клиенту идёт **образ из CI**,
а не собранный на коленке: у локальной сборки другая механика слоёв, и
расхождения там уже ловились.

Токен на чтение пакетов владелец выдаёт разовый (`read:packages`). Заводим
вход, тянем образ, вход убираем — дальше он не нужен, потому что образ
закреплён дайджестом и сам не обновится.

```bash
printf '%s' '<токен-на-чтение>' | docker login ghcr.io -u <логин> --password-stdin
DIGEST='sha256:<дайджест-от-владельца>'
docker pull "ghcr.io/ceremoneymeister-bit/korra.twenty.one@${DIGEST}"
docker logout ghcr.io
```

Закрепить образ для скриптов:

```bash
echo "ghcr.io/ceremoneymeister-bit/korra.twenty.one@${DIGEST}" > /opt/korra/IMAGE
```

**Проверка:**

```bash
docker image inspect "$(cat /opt/korra/IMAGE)" --format '{{.Id}} {{.Size}}'
```

Дайджест — не украшение: тег `:main` завтра указывает на другой образ, а
файл `IMAGE` с дайджестом даёт воспроизводимость и понятный откат.

Образ берите не старее того, в котором появились шаблоны первого запуска
(`korra-config.yaml.example`, `korra-env.example`). В образе без них подстановка
молча берёт апстримовый файл на 107 КБ, и контур застывает с чужими
умолчаниями: английское распознавание речи и модель ответа через OpenRouter.
Обновление образа этот файл уже не исправит — он принадлежит контуру.

## Шаг 5 [клиент]. Ключи и токены

Контур обустраивается сам. На первом запуске он кладёт в каталог данных
`config.yaml` и `.env` из наших шаблонов `korra-config.yaml.example` и
`korra-env.example` (корень репозитория): короткие, по-русски, с верными для
Korra умолчаниями — русское распознавание речи вшитой моделью и мультиплекс
профилей, без которого у вкладок агентов нет чата. Дальше эти файлы
принадлежат контуру, обновление образа их не переписывает.

Отсюда два равноправных пути, выбор за оператором.

**Путь А, контур поднимается уже настроенным.** Кладём заполненный `.env` до
первого запуска: заготовка подставляется только когда файла нет вовсе, так
что наш файл её вытеснит.

```bash
cp /opt/korra/env.template /opt/korra/data/.env
chown 10000:10000 /opt/korra/data/.env
chmod 600 /opt/korra/data/.env
nano /opt/korra/data/.env
```

**Путь Б, ключи вводит панель.** Не кладём ничего и идём на шаг 6. Контур
поднимется со своей заготовкой и на первое сообщение в чат честно ответит, что
провайдер не настроен (шаг 7). Ключ добавляется в панели, в разделе «Ключи»,
она пишет в тот же `.env`.

Путь А удобнее, когда контур передаётся клиенту готовым: первое же сообщение
получает ответ. Путь Б короче и не требует держать ключ в буфере обмена на
чужой машине.

Что заполнять по пути А — расписано внутри `env.template`. Обязателен только
ключ провайдера; Telegram нужен, если клиенту нужен бот; Deepgram
необязателен, без него речь распознаётся локально моделью из образа.
`API_SERVER_KEY` оставьте пустым, контур создаст его себе сам.

### Общий OAuth-клиент Google Workspace

OAuth-клиент Ceremoneymeister устанавливает только root-оператор хоста. Он
хранится вне DATA, не входит в образ и монтируется `up.sh` отдельным read-only
file mount. Контур Google запускается через `host-bootstrap.py --no-admin`:
это отзывает agent-held host-root grant, который иначе позволил бы изменить
исходный host-файл. Числовая группа должна совпадать с `KORRA_GID` контейнера
(по умолчанию `10000`):

```bash
runtime_gid=10000
install -d -o root -g "$runtime_gid" -m 0750 /opt/korra/google
install -o root -g "$runtime_gid" -m 0640 \
  /root/ceremoneymeister-google-oauth.json \
  /opt/korra/google/oauth_client.json
stat -c '%U:%g %a %n' \
  /opt/korra/google \
  /opt/korra/google/oauth_client.json
```

При bootstrap добавьте `--no-admin` и в `--plan`, и в исполняющую команду.
`up.sh` откажется монтировать Google credential при `AGENT_SUDO=1`, потому что
в штатном bootstrap этот режим связан с действующим host-root grant. Root
внутри контейнера без `CAP_SYS_ADMIN` не может перемонтировать read-only file;
граница владельца завершается отзывом отдельного SSH-доступа к host root.

Ожидаемый контракт: каталог `root:<KORRA_GID> 750`, файл
`root:<KORRA_GID> 640`. Launcher проверяет контракт и монтирует файл в
`/run/korra-secrets/google-oauth-client.json` с флагом `readonly`; core также
проверяет exact read-only mount. Credential не создаётся и не принимается из
модели, панели или `setup.py`.

**Проверка** (для пути А):

```bash
stat -c '%u:%g %a' /opt/korra/data/.env     # 10000:10000 600
grep -c '^[A-Z_]*=..' /opt/korra/data/.env  # число заполненных строк
```

## Шаг 6 [клиент]. Первый запуск

Установите параметры один раз и сначала получите план без изменений.
Имя контейнера, DATA и порты должны совпадать с будущим маршрутом кабинета.
Образ уже закреплён на шаге 4; CLI проверяет Linux/amd64.

```bash
python3 /opt/korra/host-bootstrap.py bootstrap --plan \
  --home /opt/korra --data /opt/korra/data --name korra \
  --image "$(cat /opt/korra/IMAGE)" --ssh-port 22

python3 /opt/korra/host-bootstrap.py bootstrap \
  --home /opt/korra --data /opt/korra/data --name korra \
  --image "$(cat /opt/korra/IMAGE)" --ssh-port 22
```

Штатный режим передаёт launcher значение AGENT_SUDO=1 и создаёт отдельный
ключ хоста для native install_id. Host key берётся оператором локально и
закрепляется до первого соединения. Успех требует root-проверки внутри
контейнера и через SSH из контейнера. Заблокированная учётная запись root
останавливает preflight: CLI не меняет глобальную политику root.

Для режима без администрирования добавьте --no-admin к обеим командам:
launcher получит AGENT_SUDO=0, host grant не создаётся. Непосредственный up.sh
сохраняет прежний дефолт AGENT_SUDO=0. Режим существующего контейнера CLI
не меняет незаметным recreate; используйте контролируемое обновление.

**Проверка** административной установки:

```bash
python3 /opt/korra/host-bootstrap.py verify \
  --home /opt/korra --data /opt/korra/data --name korra \
  --image "$(cat /opt/korra/IMAGE)" --ssh-port 22
docker ps --filter name=korra --format '{{.Names}} {{.Status}} {{.Image}}'
```

Порт панели по умолчанию 9119. Изменение требует согласовать ограничение
permitopen ключа кабинета на шаге 9. Ротация и отзыв root-доступа, включая
уже открытые SSH-сессии, описаны в [host-admin-setup.md](../host-admin-setup.md).

### Почему host-сеть, а не мост

Контейнер запускается с `--network host`, панель слушает `127.0.0.1:9119`.
Это не наследие, а единственный режим, в котором работает наш кабинет.

Кабинет входит на контур по SSH, пробрасывает порт панели к себе и забирает
пропуск сессии из HTML главной страницы. Движок отдаёт пропуск в HTML **только
при бинде на петлю**: любой не-петлевой бинд (`0.0.0.0`) безусловно включает
гейт авторизации, и токен из страницы пропадает — это июньское ужесточение
после кампании с открытыми панелями, `--insecure` его больше не отключает.

Мост же требует бинда на `0.0.0.0` внутри контейнера, иначе опубликованный
порт не достучится до петли контейнера. То есть «мост» и «кабинет» несовместимы
без отдельной авторизации панели, которой у клиентских контуров нет.

В host-сети агент видит loopback хоста и локальные службы. Контур устанавливают
на выделенный сервер. Режим администрирования задаёт оператор на шаге 6;
полные root-права дают агенту возможность менять хост и создавать независимые
способы доступа. Отзыв штатного ключа закрывает управляемые SSH-сессии,
но не отменяет действия уже скомпрометированного root.

Наружу host-сеть ничего не открывает: панель и служебный API привязаны к
`127.0.0.1`, а межсетевой экран из шага 1 закрывает остальное.

## Шаг 7 [клиент]. Провайдер модели

Начните с сообщения в чат панели. Свежий контур без провайдера отвечает на
него словами:

> Провайдер ответа не настроен: добавьте ключ в разделе «Ключи» или выберите
> провайдера и модель командой «korra model».

Это и есть указатель на шаг. Если такой ответ пришёл — контур жив, панель и
шлюз работают, не хватает только провайдера. Если вместо ответа тишина или
ошибка о недоступном шлюзе, дело не в ключе, и разбираться надо с шага 6.

Порядок и форма секции — в `PROVIDER.md`. Коротко: ключ в `.env` (шаг 5), в
`config.yaml` дописывается описание провайдера и выбирается модель, после чего
контейнер перезапускается. В заготовке `config.yaml`, которую контур положил
себе сам, этот пример уже лежит закомментированным — остаётся раскомментировать
и подставить адрес прокси этого контура.

**Проверка:**

```bash
docker exec -u 10000 korra sh -c 'korra config get model'
docker exec -u 10000 korra sh -c 'korra doctor' | tail -20
```

Живая проверка одна: то же сообщение в чате панели теперь получает ответ
модели, а не карточку про ненастроенного провайдера. Если карточка осталась,
смотрите `PROVIDER.md`, раздел «Если ответа нет».

## Шаг 8 [клиент]. Telegram-бот

Если шли путём А, токен и список разрешённых уже в `.env`; по пути Б впишите
их сейчас, руками или через раздел «Ключи» в панели. Адаптер включается самим
фактом наличия `TELEGRAM_BOT_TOKEN`, отдельной настройки не требует.

`TELEGRAM_ALLOWED_USERS` заполняйте всегда. Без списка бот отвечает незнакомцу
кодом привязки, и доступ решается вручную; со списком чужие сообщения молча
отбрасываются. Числовой ID клиент узнаёт у `@userinfobot`.

После правки `.env`:

```bash
docker restart korra
```

**Проверка:** клиент пишет боту «привет» и получает ответ. Затем:

```bash
docker logs --tail 30 korra | grep -i telegram
```

## Шаг 9 [наш]. Маршрут в кабинете

Выполняется на нашем сервере, где живёт кабинет (`/opt/korra-cabinet`).

Сначала алиас контура в `~/.ssh/config` — имя алиаса это фамилия клиента:

```
Host ivanov
    HostName <ip-клиента>
    Port 22
    User root
    IdentityFile /root/.ssh/<мастер-ключ>
```

Завести кабинет (реестр правится только через CLI, руками `var/clients.json`
не трогаем — пароль там лежит хэшем и восстановлению не подлежит):

```bash
/opt/korra-cabinet/cabinet-cli.py add ivanov --title "Иван Иванов" --ssh ivanov
```

CLI напечатает логин и пароль один раз. Уложить ключ туннеля на контур:

```bash
/opt/korra-cabinet/deploy-key.sh ivanov
```

Ключ ложится с ограничениями: только с адресов нашего сервера, только проброс
порта, только на `127.0.0.1:9119`, оболочка закрыта. Скрипт сам проверит, что
оболочка действительно закрыта.

Если панель на контуре не на 9119, к строке ключа в `~/.ssh/authorized_keys`
на контуре нужно дописать второе `permitopen="127.0.0.1:<порт>"` — CLI такой
порт не подставляет.

**Проверка:**

```bash
/opt/korra-cabinet/deploy-key.sh --check ivanov
/opt/korra-cabinet/cabinet-cli.py check ivanov
```

Вторая команда поднимает туннель по-настоящему и печатает версию панели.
Затем — вход браузером на `https://korra.ceremoneymeister.xyz/c/ivanov/` с
выданным паролем.

## Шаг 10 [клиент]. Бэкап в облако клиента

Настроить `rclone` на облако клиента (его учётка, не наша):

```bash
rclone config          # завести remote, например client-cloud
rclone lsd client-cloud:   # проверка доступа
```

Затем в `/opt/korra/backup.sh` заполнить `RCLONE_REMOTE` (например
`client-cloud:korra-backup`) и поставить в расписание:

```bash
crontab -l 2>/dev/null | grep -q korra/backup.sh || \
  ( crontab -l 2>/dev/null; echo '15 4 * * * /opt/korra/backup.sh >> /var/log/korra-backup.log 2>&1' ) | crontab -
```

Архив собирает штатная команда движка: она снимает базы через безопасный
механизм SQLite, а не копирует файл под работающей записью.

**Проверка — первый прогон руками:**

```bash
/opt/korra/backup.sh
ls -lh /opt/korra/data/backups/
rclone ls client-cloud:korra-backup | tail -5
```

В архив попадает `.env`, то есть ключи. Хранилище должно быть приватным; если
клиент хочет шифрование, это делается его же `rclone` (тип remote `crypt`), а
не нашим скриптом.

Из архива исключены восстановимые вещи: кеши, `__pycache__`, служебные файлы
баз и `lazy-packages` (пакеты устанавливаются заново штатным launcher).
Переносимый ZIP хранит пользовательские данные; полный offline snapshot
updater дополнительно сохраняет зависимости для отката того же контура.

## Шаг 11. Как убедиться, что всё работает

Сводная проверка, по ней и передаём контур:

| Что | Как | Что ожидаем |
|---|---|---|
| Контейнер | `docker ps --filter name=korra` | статус `Up`, тот же дайджест, что в `IMAGE` |
| Панель | `curl -fsS http://127.0.0.1:9119/api/status` | ответ JSON |
| Кабинет | вход на `/c/<slug>/` в браузере | панель открывается, чат отвечает |
| Модель | сообщение в чате панели | ответ модели, а не карточка «Провайдер ответа не настроен» |
| Telegram | сообщение боту от клиента | пришёл ответ |
| Чужой в Telegram | сообщение боту с постороннего аккаунта | ответа нет |
| Голос | голосовое боту или запись в панели | вернулся русский текст |
| Расписание | `docker exec -u 10000 korra sh -c 'korra cron list'` | команда отвечает, не падает |
| Права агента | `docker exec -u 10000 korra sh -c 'sudo -n id -u'` | отказ (при `AGENT_SUDO=0`) |
| Хост | `docker exec -u 10000 korra sh -c 'ssh host id'` | отказ (доступ не выдан) |
| Бэкап | `/opt/korra/backup.sh` и `rclone ls` | архив появился в облаке |
| Живучесть | `reboot`, через 2 минуты `docker ps` | контейнер поднялся сам |

Отдельно — восстановление. Используйте штатный `korra import` при полностью
выключенном целевом DATA: gateway, dashboard/API, cron, профили и любые SQLite
клиенты должны быть закрыты. Команда проверяет все открытые файлы, каталоги и
mmap через полный Linux `/proc` хоста; неизвестная видимость или таймаут
означают отказ. Обычный `docker exec` с отдельным PID namespace для этого
не подходит. Остановленные сервисы и их supervisor должны оставаться
выключенными до конца операции: проверка процессов не запрещает внешнему
оператору запустить нового писателя после проверки.

Сначала импорт, затем проверка данных и только после неё первый запуск.
Пример для **отдельного тестового контура**, который ещё не запущен:

```bash
# IMAGE — проверенный точный digest; архив держим вне целевого DATA.
install -d -o 10000 -g 10000 -m 750 /opt/korra-restore/data
docker run --rm --network none --pid=host --cap-add SYS_PTRACE --user 0 \
  --entrypoint /opt/hermes/.venv/bin/python \
  -e KORRA_HOME=/opt/data -e HOME=/tmp/korra-restore-home \
  -v /opt/korra-restore/data:/opt/data \
  -v /opt/korra/incoming/backup.zip:/backup.zip:ro \
  "$IMAGE" -m korra_cli.main import /backup.zip --force
```

Импорт проверяет структуру, пути, CRC и лимиты всего ZIP (100 тысяч записей,
4 ГиБ на файл, 32 ГиБ суммарно, сжатие до 1000:1), затем все SQLite через
`quick_check` во временной папке вне DATA. Повреждённый архив не меняет DATA.
Частичная ошибка публикации откатывает файлы с сохранением исходных inode;
при ошибке самого отката команда оставляет приватные recovery-каталоги и
сообщает их расположение. До ручного восстановления не запускайте сервисы.

`HERMES_HOME`/`KORRA_HOME` и `-p <profile>` выбирают ровно одну целевую
папку; корень и соседние профили не заменяются. Состояние процессов, lock/socket/
drain/restart markers и архивные WAL/SHM/journal не переносятся. Внешние файлы
провайдера памяти из `_external/` возвращаются относительно `HOME`; для их
восстановления задайте отдельный постоянный HOME и смонтируйте его, сохраняя
полную видимость процессов хоста.

По умолчанию это перенос в **новый контур**: его существующие `.ssh` и
`install_id` сохраняются, архивные ключи и installation identity пропускаются.
Для восстановления **того же контура** после проверки operator trust inventory
явно добавьте `--same-host-restore`. Каталог `.ssh` получает 0700, ключи 0600
и владельца целевого DATA; архивные executable/setuid/setgid bits не применяются.
Host-root registration и revoke/rotation выполняет оператор отдельно через
host kit; импорт сам не выдаёт доступ к хосту.

Перед первым запуском тестового контура отключите восстановленные внешние
интеграции и расписания, чтобы они не начали работу от имени production.
В частности, удалите значение `TELEGRAM_BOT_TOKEN` во всех импортированных
`.env` и проверьте `cron/jobs.json`. После этой проверки:

```bash
NAME=korra-restore DATA=/opt/korra-restore/data PANEL_PORT=9129 API_PORT=8660 \
  /opt/korra/up.sh
```

Проверьте панель, историю и список агентов. Сам `korra import` не запускает
сервисы ни после успешного восстановления, ни после ошибки.

## Шаг 12. Обновление установленной Korra

Рядом с `up.sh` установите root-owned `update.sh`, `updater.py`,
`dependencies.lock.json` и `backup.sh`. Каталог управления принадлежит root,
не доступен агенту на запись и находится вне DATA. На хосте нужны Python 3
(стандартная библиотека), Docker и свободное место под три копии данных,
образ и 2 ГБ запаса. `up.sh` используется для первого запуска; существующий
контейнер обновляет `update.sh`.

Существующий настроенный клиентский `up.sh` нельзя заменять шаблоном вслепую.
При установке host kit сохраните и перенесите фактические NAME/DATA, порты,
TIMEZONE, ENGINE_UID/GID, AGENT_SUDO и дополнительные настройки доступа;
сверьте их с работающим контейнером. Функции нового launcher добавляются с
сохранением настроек конкретной установки.

```bash
NAME=korra DATA=/opt/korra/data PANEL_PORT=9119 API_PORT=8650 \
  /opt/korra/update.sh --update ghcr.io/ceremoneymeister-bit/korra.twenty.one@sha256:… \
  --job-id release-20260907 --detach
/opt/korra/update.sh --status release-20260907
# Доставка без registry token: архив docker save, ровно один образ.
/opt/korra/update.sh --update /opt/korra/incoming/release.tar --detach
# Кабинет связывает запрос с текущей установкой и точным артефактом:
/opt/korra/update.sh --update /opt/korra/incoming/release.tar \
  --expected-current sha256:… --expected-target sha256:… \
  --expected-archive-sha256 <64-hex> --detach
# Проверка цели/места без pull, drain, остановки и изменения данных:
/opt/korra/update.sh --update sha256:… --dry-run
```

Переменные NAME/DATA/PANEL_PORT/API_PORT должны совпадать во всех вызовах.
Для отдельной установки их хранит root-owned конфигурация ограниченного
исполнителя. `--capabilities` возвращает версию машинного протокола без
Docker/данных и без побочных эффектов.

`--expected-current` — сравнение с фактическим Docker image ID под блокировкой
цели до pull/drain. Оно отклоняет устаревшее действие из кабинета после ручной
смены образа. Для tar `--expected-archive-sha256` проверяется до load и повторно
после него; `--expected-target` сверяется с фактическим `.Id` Docker до drain.
Все ожидания вместе с режимом dry-run входят в неизменяемую identity job:
повтор того же job ID с другим ожиданием возвращает ошибку.

Updater проверяет точные имя, bind DATA → `/opt/data`, команду gateway,
сетевой режим, порты и совпадение IMAGE с работающим image ID. Сначала он
скачивает/загружает образ, фиксирует полный image ID (для tar — также SHA256
архива), проверяет нативные импорты и встроенные навыки в изолированном
контейнере без данных и сети. Затем штатный gateway drain закрывает приём и
ждёт все ходы, включая API и cron. Таймаут отменяет drain и оставляет
работающий контейнер. Старые версии без полного API drain отклоняются до
остановки: для них требуется отдельно проверенный переходный выпуск.

Формат Docker image ID зависит от image store: containerd может возвращать
digest OCI index, классический store — digest config. Updater проверяет
цепочку SHA256 index → manifest → config в архиве и сверяет фактический `.Id`
Docker с этой цепочкой. До скачивания кандидата старый образ получает
уникальный локальный тег `korra-local-rollback:<job-hash>`; кандидат также
получает собственный тег. Смена общего build/latest тега сохраняет оба
образа операции доступными. Локальные теги снимаются вместе с архивом операции
только после отдельной проверки нужных данных и резервной копии.

После drain контейнер останавливается, updater делает полный offline
snapshot DATA. SQLite-файлы определяются по заголовку, копируются через
SQLite backup и проходят quick_check; проверяется SHA256 каждого файла.
SQLite открывает только уже скопированный файл: source/before остаются
неизменными, включая отсутствие новых WAL/SHM от read-only соединения.
Снимок включает зависимости и browser auth, которые переносимый `korra backup`
намеренно исключает. Ежедневный `backup.sh` продолжает использовать штатный
переносимый архив; эти два формата имеют разные цели.

До очистки и переключения образа выполняется offline rehearsal: копии
`state.db` корня и профилей открываются нативным `SessionDB` кандидата,
проходят его миграции, проверку ожидаемых колонок и integrity_check. В
контейнер без сети и gateway монтируются только копии БД; конфигурация и файлы
авторизации туда не переносятся. Receipt
`schema-rehearsal.json` фиксирует проверенные БД и версии схем. Эта проверка
покрывает native session DB; собственные БД плагинов требуют приёмки их
механизмов миграции. Обратные миграции не предполагаются: откат использует before.

Только после проверенного snapshot удаляются осиротевшие встроенные навыки:
имя должно присутствовать в старом manifest, native hash и все SHA256 файлов
должны совпадать со старым образом. Изменённые/пользовательские навыки,
`.no-bundled-skills`, `.pin`/`.pinned` сохраняются. `up.sh` прогревает точные
версии документного стека через `tools.lazy_deps.install_specs` в DATA до
старта gateway, проверяет версии/импорты в отдельном процессе. Native constraints
сохраняют версии core venv образа; прежние durable versions не подмешиваются
в этот список, поэтому закреплённые пакеты можно обновить.

CPU/RAM лимиты первого запуска опциональны: по умолчанию launcher их не задаёт.
Updater сохраняет фактические HostConfig NanoCpus/Memory в receipt и переносит
их при обновлении, включая `0` (без ограничения). Явные операторские
`CONTAINER_CPUS=4`, `CONTAINER_MEMORY=4g` считаются намеренным override для
обновления; rollback всегда возвращает исходные лимиты, даже при заданных env.

UID/GID и AGENT_SUDO тоже фиксируются по фактическому контейнеру. Обновление
сохраняет их; только явный AGENT_SUDO меняет forward mode, rollback возвращает
исходный. Изменение UID/GID через env отклоняется до pull/drain. Для снятия
managed host-root сначала используйте host-bootstrap.py revoke; снятие sudo
внутри контейнера и отзыв host key — отдельные границы.

До pull/drain updater сохраняет baseline_capability: foundation только при
нативном AuthError/no_provider_configured; configured при успешном разрешении
провайдера. Receipt хранит SHA256 идентичности provider/endpoint/API mode без
ключа или адреса. Отсутствующий ключ явно выбранного провайдера, повреждённая
авторизация и неопределённость отклоняются до остановки.

После запуска одинаковый smoke для forward и rollback проверяет панель,
обязательные gateway/dashboard/storage/platforms components и overall=ok,
точную актуальную config schema, live gateway socket, список и покрытие прежних
served_profiles. Затем capability должна совпасть с baseline. Foundation
проверяет stateless SSE с ожидаемым русским missing-provider error и [DONE],
без model ACK; configured обязан получить KORRA_UPDATE_OK от модели.
Degraded/malformed/missing health не маскируется успешной моделью.
Native readiness ожидается до WAIT_SECONDS: готовая панель может опережать
gateway и профили. Смена identity/ресурсов и остановка контейнера сразу
считаются ошибкой. Capability probe ограничен 30 секундами, API smoke — 90.
Старый receipt без baseline_capability не разрешает автоматический rollback:
оператор проверяет сохранённую операцию отдельно, режим не угадывается.
Этот запрос не доставляется людям или в каналы. Для CI/стенда
используется отдельный локальный fake-model endpoint и синтетические ключи.
Приёмка кандидата на данных клиента выполняется только через sanitizer всех
профилей и расписаний; нельзя запускать простой `cp` рабочего HOME с ботами.

`--detach` отделяет процесс от SSH/браузера, сохраняя блокировку цели до
завершения. Закрытие браузера не отменяет операцию. Одновременно выполняется
одна операция на DATA; повтор того же job ID возвращает существующий receipt.
Хостовый reboot/SIGKILL требует проверки сохранённой фазы оператором, автоматическое
повторение незавершённого изменения данных не выполняется.

`updates/<job-id>/status.json` — машинный receipt; `updates.log` — общий журнал;
`operation.log`/`worker.log` в каталоге операции — root-only диагностика.
Статусы: pending, running, succeeded, failed, rolled_back, rollback_failed.
Не выгружайте внутренние снимки и журналы в браузер: они содержат данные клиента.

## Шаг 13. Откат выпуска

```bash
/opt/korra/update.sh --rollback release-20260907 --detach
/opt/korra/update.sh --status release-20260907
```

Откат возвращает предыдущий image ID и проверенный snapshot перед обновлением.
Обратные миграции схемы движка не предполагаются. Более новые `auth.json`,
`.env`, token/credential/session и browser-cookie хранилища сохраняются;
отозванные файлы не воскрешаются из старой копии. Все данные после обновления
экспортируются в `updates/<job-id>/after/`; перечень отличий хранится в
`post-update-changes.json`. Исходный каталог также остаётся рядом как
`data.after-<job-id>`. Новые деловые записи доступны в экспорте для сверки и
переноса оператором: автоматического слияния баз разных схем нет.

Код библиотек, lazy-packages, venv и package caches не считаются credentials
по словам token/cookie/auth в именах. Канонические BWS cache и `.secrets`
сохраняются. Новые каталоги настоящих секретов получают owner/mode из latest,
чтобы приватный umask хостового worker не закрывал доступ пользователю движка.

Образ и данные откатываются автоматически при неудачной приёмке. Если нельзя
подтвердить drain, подлинность snapshot или цель, операция останавливается с
`rollback_failed` и сохранёнными данными. `IMAGE.prev` — диагностический указатель;
сам по себе он не заменяет откат данных. Snapshot и exports удаляются только
после отдельной проверки нужных записей и резервной копии.

**Закрыть кабинет** (на нашем сервере) — без удаления записи:

```bash
/opt/korra-cabinet/cabinet-cli.py disable ivanov
```

Снять ключ туннеля с контура — убрать из `~/.ssh/authorized_keys` строку с
меткой `korra-cabinet@ceremoneymeister` или вернуть `.bak`-копию, которую
оставляет `deploy-key.sh`.

**Снести контур целиком:**

```bash
docker rm -f korra
# данные остаются в /opt/korra/data — удалять только после выгрузки архива
```

## Release gate: exact-SHA full CI

Publish зависит от отдельного job full-ci: registry credentials недоступны
publish job, пока GitHub Actions API не подтвердит completed/success полного
ci.yaml на том же SHA. Учитывается последний manual/scheduled run, его exact
attempt и все обязательные native jobs, включая Python, JS, lint, Rust,
lockfile и итоговый aggregate. PR, missing/red/cancelled, skipped mandatory
lane, иной SHA/fork/workflow и неполный rerun не дают разрешения. Старый green
не заменяет более новый red. Receipt сохраняется в artifact full-ci-receipt.
Новый runtime updater/image через этот gate не собирается: build → accepted
archive SHA/image ID/source revision → load/publish остаются одной цепочкой.

CI и Docker используют общий repository-wide concurrency group с
cancel-in-progress=false. Они не ждут друг друга внутри lease: без готового
CI release gate сразу отказывает. Перед началом detect общий read-only
admission требует load1 ≤ 6, MemAvailable ≥ 6 GiB и диск ≥ 20 GiB.
Оператор запускает полный CI первым, затем отдельный Docker workflow.
Обновление групп начинает защищать оба workflow после доставки новой CI
конфигурации в соответствующие refs; старые runs по прежнему YAML нужно
дождаться до ручного прогона. Внутри CI сохраняются нативные лимиты workers.

Семантика опирается на [GitHub workflow runs API](https://docs.github.com/en/rest/actions/workflow-runs),
[jobs конкретной попытки](https://docs.github.com/en/rest/actions/workflow-jobs#list-jobs-for-a-workflow-run-attempt)
и [workflow concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency).
Никакие registry/deploy действия не выполняются самим release_gate.py.
