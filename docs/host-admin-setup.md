# Доступ агента к хост-системе: процедура для оператора

Агент Korra 21 живёт в контейнере. Внутри контейнера право root ему даёт
`sudo` без пароля (это дефолт образа, см. `Dockerfile` и выключатель
`KORRA_AGENT_SUDO` в `docker/stage2-hook.sh`). Хост — отдельный контур, и
доступа к нему у агента по умолчанию **нет**: ни ключа, ни алиаса образ не
содержит и хук на загрузке не создаёт. Он заводит только пустой каталог
`$HERMES_HOME/.ssh` с режимом 700.

Эта процедура включает доступ к хосту. Выполняет её человек, у которого уже
есть root на хосте. Агент её не выполняет и выполнить не может — в этом и
смысл: право администрировать машину выдаётся снаружи, а не берётся изнутри.

Бандл-скилл `skills/ops/server-admin` учит агента пользоваться результатом и
первым делом проверять, настроен ли доступ вообще.

## Когда это нужно

Только когда владелец контура — он же владелец сервера, и он сознательно
хочет администрировать машину через чат или панель. Для клиентского контура
это не нужно: там агент работает внутри контейнера, а хост остаётся чужим.

## Что понадобится

- root на хосте;
- на хосте разрешён вход по ключу (`PubkeyAuthentication yes`) и root-логин
  хотя бы по ключу (`PermitRootLogin prohibit-password` достаточно);
- в образе есть клиент ssh — он там штатно (`openssh-client`).

## Шаг 0. Узнать, каким адресом контейнер видит хост

От этого зависит и адрес в конфиге, и ограничение ключа.

```bash
docker inspect <контейнер> --format 'NetworkMode={{.HostConfig.NetworkMode}}'
```

- `host` — контейнер делит сетевой стек с хостом. Адрес хоста для него
  `127.0.0.1`, ограничение ключа — `from="127.0.0.1"`.
- `bridge` или своя сеть — адрес хоста это шлюз моста, ограничение — подсеть
  моста:

```bash
docker inspect <контейнер> \
  --format '{{range .NetworkSettings.Networks}}{{.Gateway}} {{end}}'
docker network inspect bridge --format '{{range .IPAM.Config}}{{.Subnet}}{{end}}'
```

Дальше в примерах `host`-сеть и `127.0.0.1`. Для моста подставьте свои
значения.

## Шаг 1. Ключ в томе с данными

Ключ кладётся в каталог данных, а не в слой контейнера: пересоздание
контейнера его не должно уносить. Владелец файлов — uid пользователя движка
(по умолчанию 10000, либо ваш `HERMES_UID`).

```bash
DATA=/root/.korra21          # каталог, смонтированный в /opt/data
UID_ENGINE=10000             # ваш HERMES_UID, если он переопределён

mkdir -p "$DATA/.ssh"
chown "$UID_ENGINE:$UID_ENGINE" "$DATA/.ssh"
chmod 700 "$DATA/.ssh"

ssh-keygen -t ed25519 -N '' -C 'korra21-host-admin' \
    -f "$DATA/.ssh/id_ed25519_host"

chown "$UID_ENGINE:$UID_ENGINE" "$DATA/.ssh/id_ed25519_host" \
                               "$DATA/.ssh/id_ed25519_host.pub"
chmod 600 "$DATA/.ssh/id_ed25519_host"
chmod 644 "$DATA/.ssh/id_ed25519_host.pub"
```

Ключ без парольной фразы намеренно: агент неинтерактивен, вводить фразу
некому, а `BatchMode=yes` в конфиге ниже всё равно запрещает любые вопросы.
Защита ключа здесь — не парольная фраза, а права на файл и ограничение
`from=` на стороне хоста.

## Шаг 2. Конфиг ssh с алиасом `host`

У движка `HOME=/opt/data`, поэтому `~/.ssh/config` — это
`$DATA/.ssh/config`, и ssh подхватывает его сам, без флага `-F`.

```bash
cat > "$DATA/.ssh/config" <<'EOF'
Host host korra-host
    HostName 127.0.0.1
    Port 22
    User root
    IdentityFile /opt/data/.ssh/id_ed25519_host
    IdentitiesOnly yes
    StrictHostKeyChecking accept-new
    UserKnownHostsFile /opt/data/.ssh/known_hosts
    BatchMode yes
    ConnectTimeout 10
    ControlMaster auto
    ControlPath /opt/data/.ssh/cm-%r@%h-%p
    ControlPersist 300
    ServerAliveInterval 30
EOF
chown "$UID_ENGINE:$UID_ENGINE" "$DATA/.ssh/config"
chmod 600 "$DATA/.ssh/config"
```

Пути внутри файла — как их видит контейнер (`/opt/data/...`), а не как их
видит хост.

Зачем каждая строка:

- `IdentitiesOnly yes` — иначе ssh переберёт все известные ключи и может
  упереться в лимит попыток аутентификации, не дойдя до нужного.
- `StrictHostKeyChecking accept-new` — первое подключение не должно висеть на
  вопросе о подлинности хоста; дальше ключ хоста зафиксирован.
- `BatchMode yes` — никаких вопросов о пароле: у агента нет терминала, вопрос
  превратился бы в зависание на весь таймаут.
- `ControlMaster` — серия коротких команд не платит за новый хендшейк каждый
  раз.

## Шаг 3. Публичный ключ на хост, с ограничениями

Сначала резервная копия — она же путь отката.

```bash
cp -a /root/.ssh/authorized_keys \
      /root/.ssh/authorized_keys.bak-$(date +%Y%m%d)
```

Затем строка. Ограничения обязательны, это не украшение:

```bash
KEY=$(cat "$DATA/.ssh/id_ed25519_host.pub")
printf '%s\n' \
  "from=\"127.0.0.1\",no-agent-forwarding,no-X11-forwarding $KEY" \
  >> /root/.ssh/authorized_keys
chmod 600 /root/.ssh/authorized_keys
```

- `from="127.0.0.1"` (или подсеть моста) — утёкший приватный ключ бесполезен
  снаружи машины. Ставьте самое узкое, что работает: адрес контейнера точнее
  подсети, подсеть точнее ничего.
- `no-agent-forwarding` — проброс агента это классический канал кражи чужих
  ключей, администрированию он не нужен.
- `no-X11-forwarding` — графики здесь нет вовсе.
- `command=` намеренно **не** ставится: смысл доступа именно в произвольном
  администрировании. Если нужен узкий доступ под одну задачу — ставьте
  `command=` и получите другой, более безопасный сценарий.

## Шаг 4. Проверить

Обязательно от имени пользователя движка, а не root: у root внутри
контейнера другой `HOME`, и проверка получилась бы неверной.

```bash
docker exec -u 10000 <контейнер> sh -lc 'ssh host id'
```

Ожидается `uid=0(root) gid=0(root)`. Первое подключение допишет `known_hosts`
и напечатает про это предупреждение — это нормально.

Затем негативная проверка: тот же ключ не должен работать не с локального
адреса.

```bash
HOSTIP=$(ip -4 route get 8.8.8.8 | grep -oP 'src \K\S+')
ssh -i "$DATA/.ssh/id_ed25519_host" -o IdentitiesOnly=yes -o BatchMode=yes \
    "root@$HOSTIP" id
```

Ожидается `Permission denied (publickey)`. Если команда прошла — ограничение
`from=` не применилось, разбирайтесь с ним до того, как отдавать доступ
агенту.

## Откат

```bash
cp -a /root/.ssh/authorized_keys.bak-ГГГГММДД /root/.ssh/authorized_keys
rm -rf "$DATA/.ssh"
```

Действует сразу, перезапуск sshd не нужен: `authorized_keys` читается на
каждое подключение.

## Что этот доступ означает

Агент получает root на машине. Промпт-инъекция из письма, веб-страницы или
клиентского файла получает ровно столько же. На хосте с боевыми контурами
других клиентов это касается и их.

Поэтому:

- включайте это только на своей машине и только пока это нужно;
- на общем хосте считайте, что периметр агента равен периметру сервера;
- для клиентских контуров процедуру не выполняйте, а sudo внутри контейнера
  выключайте через `KORRA_AGENT_SUDO=0`.
