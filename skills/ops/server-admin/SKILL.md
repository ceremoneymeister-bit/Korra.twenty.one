# Администрирование сервера

Ты работаешь внутри контейнера, а сервер — снаружи. Это два разных контура, и
первая ошибка почти всегда одна и та же: команда уходит не туда. Скилл
объясняет, где ты находишься, как попасть в каждый контур и что там опасно.

## Два контура

| Где | Как туда попасть | Кто ты там |
|---|---|---|
| Контейнер (твой дом) | обычная команда в `terminal` | пользователь движка, root через `sudo` |
| Хост (сама машина) | `ssh host <команда>` | сразу root, `sudo` не нужен |

Проверить, где ты, можно всегда:

```bash
hostname          # имя контейнера
ssh host hostname # имя сервера
```

## Контур 1: контейнер

Обычные команды выполняются в контейнере. Права root даются через `sudo` без
пароля — просто пиши `sudo` перед командой, вопроса о пароле не будет:

```bash
sudo apt-get update && sudo apt-get install -y <пакет>
sudo ls -la /root
```

Никогда не пиши `sudo -S` и не подставляй пароль в команду. Пароль не нужен, а
такая команда будет отклонена жёстким стражем как попытка подбора пароля.

Что важно знать про файловую систему контейнера:

- `/opt/data` — данные: конфиг, профили, память, журналы, скиллы, `cron`. Всё
  это переживает пересоздание контейнера. Здесь ты и работаешь.
- `/opt/hermes` — код движка, смонтирован только на чтение и пересобирается
  вместе с образом. Правка тут либо не пройдёт, либо исчезнет при следующем
  обновлении. Если нужно поменять код — это задача на сборку образа, а не на
  `sudo` в живом контейнере.
- Установленные через `sudo apt-get` пакеты живут только до пересоздания
  контейнера. Если пакет нужен постоянно, его место в `Dockerfile`; скажи об
  этом человеку, а не ставь молча каждый раз заново.

Не меняй владельца файлов в `/opt/data` на root. Загрузочный сценарий на
каждом старте выравнивает владельца обратно на пользователя движка, и
root-owned файлы в профилях и `cron` уже приводили к тому, что контейнер
уходил в цикл перезапусков.

## Контур 2: хост

```bash
ssh host <команда>
```

Ты попадаешь туда сразу как root — `sudo` не нужен и его там может не быть в
твоём окружении. Соединение идёт по ключу из `~/.ssh/id_ed25519_host`, алиас
`host` описан в `~/.ssh/config`. Ключ принимается только с локального адреса,
поэтому за пределами этой машины он бесполезен.

Типичные задачи:

```bash
ssh host "systemctl status nginx"
ssh host "systemctl restart nginx"
ssh host "journalctl -u nginx -n 100 --no-pager"
ssh host "docker ps"
ssh host "docker logs --tail 100 <контейнер>"
ssh host "df -h; free -m; uptime"
```

Три особенности, из-за которых команды ведут себя не так, как ожидаешь:

1. **Каталог не сохраняется между вызовами.** Каждый `ssh host` — новая
   сессия. `ssh host "cd /opt/foo"` не влияет на следующую команду. Пиши
   `ssh host "cd /opt/foo && <команда>"` одной строкой.
2. **Кавычки разбирает удалённый шелл.** Всю команду бери в кавычки целиком, а
   внутри следи за экранированием — особенно в `--format` у docker.
3. **Файловые инструменты в хост не ходят.** `read_file`, `write_file`,
   `search_files` и `patch` работают с файловой системой контейнера. Чтобы
   прочитать файл на хосте, используй `ssh host "cat <путь>"`; чтобы записать —
   передай содержимое через stdin, а не собирай heredoc наугад.

## Диагностика: с чего начинать

Порядок, который экономит больше всего времени:

```bash
ssh host "systemctl is-system-running"      # общее состояние
ssh host "df -h"                            # переполненный диск — причина №1
ssh host "docker ps -a --format '{{.Names}}\t{{.Status}}'"
ssh host "journalctl -p err -n 50 --no-pager"
```

Дальше — журнал конкретной службы или контейнера. Не делай вывод о причине по
одной корреляции: найди воспроизводимый симптом и зафиксируй исходное
состояние до того, как что-то менять.

## Что опасно

На этой машине живут боевые контуры других людей. Всё, что ты делаешь на
хосте, задевает их.

Не делай без явной просьбы человека:

- останавливать, перезапускать, пересоздавать или удалять чужие контейнеры;
- перезапускать общие службы: `docker`, `nginx`, `ssh`, сеть;
- `rm -rf` по путям вне своего рабочего каталога;
- менять `sshd_config`, `authorized_keys`, правила firewall — ошибка здесь
  отрезает доступ к серверу, и починить её изнутри уже нельзя;
- `apt-get upgrade`, обновление ядра, `mkfs`, `dd`, работу с разделами.

Перезапуск своего же контейнера обрывает твою текущую сессию: ты не увидишь
результат и не сможешь доложить. Если он действительно нужен — предупреди
человека заранее.

Перед необратимым изменением зафиксируй три вещи и напиши их в ответе: что
именно меняешь, каким было состояние до, и какой командой откатить. Правку
конфига начинай с копии рядом:

```bash
ssh host "cp -a /etc/nginx/nginx.conf /etc/nginx/nginx.conf.bak-$(date +%Y%m%d)"
```

Проверяй конфиг до применения, а не после: `nginx -t`, `visudo -c -f <файл>`,
`sshd -t`. Перезагружай службу, а не перезапускай, когда это возможно
(`systemctl reload`) — так живые соединения не рвутся.

## Если команда отклонена

Опасные команды проходят через контроль одобрений, и отказ выглядит как
сообщение, начинающееся с `BLOCKED`. Читай его целиком, там сказано, какой
именно страж сработал:

- **жёсткий страж** (catastrophic, `sudo -S`) — обойти нельзя ничем, и это
  правильно. Переформулируй задачу, а не команду.
- **правило запрета** из настроек — тоже не обходится. Скажи человеку, какое
  правило мешает.
- **нет человека, который может одобрить** — команда пришла с поверхности без
  интерактивного подтверждения. Это настраивается человеком в `config.yaml`
  (`approvals.unattended_mode`), сам не обходи.

Ни при каких обстоятельствах не пытайся обойти отказ: не дроби команду на
части, не прячь её в скрипт, не кодируй в base64. Если отказ мешает делу —
скажи об этом прямо и объясни, что именно нужно разрешить и зачем.
